Harness Receipts

A harness is the fixed set of steps an AI coding agent must pass before its code merges: plan, build, agent review, an adversarial check, CI, merge. This is the weekly scorecard of one such harness, run by one developer across their own projects. Every number is a count or a sum over rows the harness already writes. No prompts, repos or files are named. The score is a health check of the setup, not a grade of the work.

What runs, and what each stage writes down

Two loops. The top one runs once per change; the bottom one measures the harness itself. Each node names the rows it produces. Token shares are this history's totals and annotate the stage that spent them.

Tokens per harness part

Share of all tokens each week by what the turn was doing. A turn is charged to its first tool call, and most tokens are cache reads, so this is the cost of carrying context through a stage, not of generating output there.

Limits, stated. One developer, one harness, a few months of rows. The score measures structure, not outcomes; the outcome numbers stop at merge time. There is no control arm, so nothing here says what the numbers would be without the harness. Token history begins when transcript mining started; earlier sessions are gone.

Definitions. A merge is a pull request merged in a repo the harness is mounted in. The build lane opens it and stops; the main loop checks CI and merges under the developer's token, so a week can hold a hundred, and "merged on red" means the loop merged although CI was not green. A credited merge is code-class with green CI at merge time. Sessions come from a roster of repos; token sessions come from every project directory including workflow worktrees, so the second count is larger. Reconstructed score points are plotted as the instrument scored them then, vacuous drift included; hover for the three-dimension number. Weeks with no rows are absent, not zero.
